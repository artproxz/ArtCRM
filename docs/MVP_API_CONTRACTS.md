# MVP API Contract Readiness For Backend-First Implementation

This document defines implementation-ready MVP API contract documentation before backend coding begins.

It is documentation only. It does not implement API routes, controllers, backend services, database schema, SQL, ORM, migrations, tests, frontend UI, dependencies, containers, integrations, real data, credentials, tokens, secrets, or business logic.

## Purpose

ArtCRM architecture already defines many conceptual DTOs and workflows. Before writing backend code, the project needs a bounded set of backend-first API contracts that enforce:

- permissions and object ownership;
- audit event emission;
- state transition guards;
- idempotency for mutating actions;
- sensitive field masking;
- LLM candidate-data boundaries;
- backend source-of-truth rules.

These contracts are not final route implementations. They are readiness contracts for future backend tasks.

## API Conventions

### Transport And Format

- JSON only for request and response payloads.
- Backend-owned APIs only.
- Frontend must not call Ollama, mail, 1C, database, cache, filesystem, catalog storage, or secrets directly.
- Service actors use scoped backend credentials and permissions, not human role shortcuts.

### Required Request Metadata

Every mutating or workflow-sensitive request should include:

| Field | Required | Meaning |
| --- | --- | --- |
| `request_id` | Yes | API correlation ID generated by caller or gateway. |
| `idempotency_key` | Required for mutating actions | Prevents duplicate state changes, imports, sends, applies, exports, or publications. |
| `actor_context` | Backend-derived | Current actor, role template, explicit grants/revokes, ownership scope. |
| `expected_state` | Recommended | Optimistic guard for state-changing operations. |
| `reason` | Required for sensitive transitions | Human-readable safe reason for override/reject/cancel/apply/publish. |

### Common Response Envelope

```json
{
  "request_id": "demo-request-id",
  "data": {},
  "errors": [],
  "pagination": null,
  "audit_event_refs": ["audit_event:demo-001"],
  "masked_fields": [],
  "state_transition": null
}
```

### Pagination, Filtering, Sorting

List endpoints should use consistent concepts:

- `page_size` and `cursor` for pagination.
- `filter` object for entity-specific filters.
- `sort` list for stable sort fields.
- Backend validates that filter fields are applicable and permitted.
- Sensitive filters such as `margin`, `purchase_price`, `supplier_discount`, staff performance, or all-counterparty export require matching permissions.

### Error Model

| Error type | Meaning | HTTP-style category for future mapping |
| --- | --- | --- |
| `validation_error` | Request shape or field value failed validation. | 400 |
| `permission_denied` | Actor lacks permission or ownership scope. | 403 |
| `state_transition_denied` | Requested transition is not allowed from current state. | 409 |
| `conflict` | Concurrent update or stale expected state. | 409 |
| `duplicate_external_id` | Import/external ID conflicts with existing object. | 409 |
| `not_found` | Entity not found or hidden by permissions. | 404/403 policy-dependent |
| `sensitive_field_masked` | Field intentionally hidden by permission masking. | 200 with masked field or 403 for direct access |
| `idempotency_conflict` | Same key used for different payload. | 409 |
| `agent_unavailable` | Agent runtime/backend orchestration unavailable. | 503 |
| `import_validation_failed` | Import preview/apply validation failed. | 422 |

Error envelope example:

```json
{
  "code": "permission_denied",
  "message": "Permission required for this action.",
  "permission_required": "pricing.view_margin",
  "field": "margin",
  "safe_details": {
    "masked": true
  }
}
```

### Audit Event Emission

- Every mutating action emits an audit event.
- Sensitive reads emit audit events when they expose purchase price, supplier discount, margin, supplier response, internal commercial document, staff performance, counterparty export, permission management, or audit export data.
- Denied sensitive actions emit safe denied-access events.
- Audit event references should be returned in response envelopes when safe.

### Sensitive Field Masking

Backend serialization must mask sensitive fields after authorization and before response delivery.

Examples:

- `purchase_price` requires `pricing.view_purchase_price`.
- `supplier_discount` requires `pricing.view_supplier_discount`.
- `margin` requires `pricing.view_margin`.
- supplier response details require `supplier_quote.view_response`.
- internal document links require `documents.view_internal` or document-specific visibility permission.
- staff performance metrics require `analytics.view_staff_performance`.
- all-counterparty export requires `counterparty.export`.

### State Transition Validation

All mutating operations that change state must:

- read current state in backend;
- validate requested transition against `MVP_STATE_MACHINES.md`;
- validate actor permission and object ownership;
- emit audit event;
- return transition result or a `state_transition_denied` error.

## API Group: Auth / Current User / Permissions

Purpose: expose current actor context and effective permissions to the frontend without making frontend the source of authorization.

Conceptual operations:

| Operation | Purpose | Mutating | Idempotency |
| --- | --- | --- | --- |
| `get_current_user` | Return safe current user profile. | No | No |
| `get_role_template` | Return role template metadata. | No | No |
| `get_effective_permissions` | Return effective permission snapshot. | No | No |
| `list_explicit_grants_revokes` | Show grants/revokes visible to actor. | No | No |
| `get_customer_context` | Return own customer/org context if applicable. | No | No |

Request shape:

```json
{
  "request_id": "demo-request-id"
}
```

Response shape:

```json
{
  "data": {
    "user_ref": "user:demo",
    "actor_type": "staff_user",
    "role_template": "manager",
    "effective_permissions": ["request.view_assigned", "quote.create_draft"],
    "explicit_grants": [],
    "explicit_revokes": [],
    "object_scopes": ["assigned", "team"],
    "customer_context": null
  },
  "masked_fields": []
}
```

Required permissions:

- Current user can view own effective snapshot.
- Viewing other users' permissions requires `admin.permissions_manage` or `audit.view` depending on context.

Audit events:

- `permission.snapshot_viewed` for sensitive/admin views.
- `permission.denied` for denied permission inspection.

Not implemented here: authentication mechanism, sessions, password reset, OAuth, email verification, middleware, user database.

Purpose: staff-side MVP request intake, review, assignment, state transition, and position management.

Conceptual operations:

| Operation | Purpose | Required permissions | Audit events |
| --- | --- | --- | --- |
| `list_requests` | List/search requests by permitted scope. | `request.view_assigned`, `request.view_team`, or `request.view_all` | sensitive read if broad scope. |
| `create_request_draft` | Create request draft from controlled input. | `request.create` | `request.created`. |
| `update_request` | Edit draft/review fields. | `request.edit` | `request.updated`. |
| `assign_manager` | Assign/reassign responsible staff. | `request.assign_manager` | `request.assigned`. |
| `change_request_status` | Change RequestCard state. | `request.change_status` | `request.state_changed`. |
| `create_position` | Create RequestPosition draft. | `request_position.create` | `request_position.created`. |
| `update_position` | Edit position fields. | `request_position.edit` | `request_position.updated`. |
| `view_source_mail_candidate_data` | View safe source/candidate refs. | `request.view_assigned` plus source scope | `request.source_viewed` if sensitive. |

Request DTO shape for status transition:

```json
{
  "request_id": "demo-api-request",
  "idempotency_key": "demo-transition-key",
  "request_card_ref": "request:demo-001",
  "expected_state": "draft",
  "target_state": "ready_for_matching",
  "reason": "Required fields reviewed by manager."
}
```

Response DTO shape:

```json
{
  "data": {
    "request_card_ref": "request:demo-001",
    "state": "ready_for_matching",
    "customer_visible_status": "in_progress",
    "positions_summary": {
      "total": 2,
      "needs_review": 0,
      "ready_for_matching": 2
    }
  },
  "audit_event_refs": ["audit_event:demo-request-state"]
}
```

State transitions:

- Must follow `RequestCard` and `RequestPosition` state machines.
- Request cannot become quote-ready while required positions remain unresolved.

Sensitive field masking:

- Source mail/candidate data may be summarized and redacted.
- Internal notes and commercial context require relevant permissions.

Not implemented here: actual endpoints, persistence, mail ingestion, frontend views, assignment engine, SLA engine.

```json

  "agent_type": "position_intent",
  "input_ref": "request_position:demo-001",
```

```json
{

    "agent_run_ref": "agent_run:demo-001",
```

State transitions:

- Must follow `AgentRun` state machine.

Not implemented here: agent orchestrator, validation service, prompt/model registry, Ollama calls, retry runtime.

## Cross-API Idempotency Requirements

Idempotency keys are required for:

- create request draft;
- create/update positions when duplicate creation is possible;
- start agent run;
- run matcher;
- create supplier quote request draft;
- send supplier quote request;
- register/apply supplier response;
- create quote draft;
- send quote;
- export quote;
- publish/unpublish customer-visible document;
- import apply;
- enrichment request/apply;
- purchase create/update/approval;
- audit export.

If the same `idempotency_key` is reused with a different payload, backend should return `idempotency_conflict`.

## Cross-API Permission And Masking Requirements

- Entity-level authorization happens before loading or mutating business data.
- Field-level masking happens before response serialization.
- Denied access must not reveal restricted data through error text, notification preview, audit metadata, or response shape.
- Service actor requests must include backend-derived service scope.
- Sensitive fields must not be returned only because a user can view the parent entity.
